# 目标审计到 Adaptive K：完整实验链

本实验回答一个比“哪个专家激活更多”更直接的问题：

> 对当前图像，选择哪个 Transformer 专家能降低检测损失；路由器能否学会这种选择，并在不明显
> 损失检测精度的前提下减少实际专家调用？

固定条件：VisDrone、完整 MoT-N、目标层 `model.14.m.0`、输入 640、checkpoint SHA-256
`a1857c81...e629`。检测器与专家始终冻结，只有目标路由器可训练。

## 1. 证据边界

| 层次 | 操作 | 能回答的问题 |
|---|---|---|
| 目标匹配审计 | 比较相似的低/高遮挡目标 | 路由与遮挡是否存在稳定关联 |
| 专家强制干预 | 同图只替换一个 MoT 层的专家 | 哪个专家对该图的检测损失更低 |
| 端到端验证 | 原图重新计算 mAP、延迟和实际调用 | 新路由是否真的可部署 |

第一层是控制协变量后的观察性审计，不构成严格因果证明；第二层才是模型内部反事实干预。当前
Ultralytics loss 不提供可靠的逐目标分解，因此效用矩阵以“单图聚合检测损失”为单位，不伪装成
逐目标效用。

## 2. 目标级审计

### 2.1 第一版

将原始 VisDrone 框投影到每个 MoT 特征图，统计框内概率、top-1 占比和框内减邻域环带概率。
低/高遮挡目标按视频序列、类别和面积配对，再以视频序列为统计单位做 paired bootstrap、
sign-flip permutation、Hedges' g 和 BH-FDR。

初跑得到 38,759 个目标、13,581 对匹配和 34/54 个显著项。

### 2.2 复审发现

1. 帧号错误取了文件名第二段，而 VisDrone 的真实帧号在末段；
2. 21.6% 配对的面积比超过 `exp(0.5)`，最大差距不可接受；
3. truncation 未控制，边界截断可能与遮挡混杂。

### 2.3 修正与复验

- 帧号改取末段；
- 视频序列、类别、truncation 精确匹配；
- 设置 `|log(area_high)-log(area_low)| <= log(2)`；
- 目标不重复使用，优先同帧，再按面积和帧距匹配。

复验保留 12,296 对、76 个序列；69.17% 为同帧配对，面积 log 差中位数 0.0541、最大
0.6923。显著项降为 22/54。

| 层 | 专家 | 高遮挡减无遮挡 | 95% CI | q | g |
|---|---|---:|---:|---:|---:|
| `14.m.0` | LocalConv，框内概率 | +0.00693 | [0.00410, 0.00968] | 0.00098 | 0.549 |
| `14.m.0` | Deformable，框内概率 | +0.00259 | [0.00149, 0.00364] | 0.00098 | 0.530 |
| `14.m.0` | Window，框内概率 | -0.00952 | [-0.01303, -0.00574] | 0.00166 | -0.583 |
| `20.m.1` | Deformable，框内概率 | +0.00066 | [0.00013, 0.00116] | 0.02211 | 0.287 |

**新结论**：遮挡会引起层相关的组合重分配；浅层 LocalConv 与 Deformable 同时增加，不能概括成
“遮挡统一切换到 Deformable”。而且激活变化仍不等于检测效用。

## 3. 检测效用矩阵

对每张图执行四次 loss：

1. 自然路由；
2. 只在目标层强制 LocalConv；
3. 强制 Window；
4. 强制 Deformable。

定义：

```text
L(i,e) = box_loss + cls_loss + dfl_loss
oracle(i) = argmin_e L(i,e)
regret(i,e) = L(i,e) - min_e L(i,e)
target(i,e) = softmax(-(L(i,e)-min L(i,*))/temperature)
```

MoT 辅助损失不进入效用，避免用路由器自身的正则项监督路由器。

### 3.1 先筛层

P5-only 的 4 图 smoke test 中，专家差异仅约 `1e-6`，没有可学习信号。随后在完整 MoT 的同一
16 图上筛六层：

| 层 | 原路由命中 oracle | 平均 regret | oracle 相对自然路由增益 |
|---|---:|---:|---:|
| `14.m.0` | 0.500 | 0.01407 | 0.02158 |
| `14.m.1` | 0.500 | 0.01247 | **0.02516** |
| `20.m.0` | 0.438 | 0.00705 | 0.01006 |
| `20.m.1` | 0.500 | 0.00804 | 0.00735 |
| `23.m.0` | 0.875 | ~0 | ~0 |
| `23.m.1` | 0.000 | 0.00003 | 0.00003 |

`14.m.0` 同时具有较大效用跨度和较高 regret，选为干预层；深层高命中但效用近零，不适合作为
训练证据。

### 3.2 扩大矩阵

| split | 图像/序列 | 原路由命中 | 平均 regret | oracle：Local/Window/Deform |
|---|---:|---:|---:|---:|
| train | 2,048 / 170 | 0.357 | 0.03380 | 36.9% / 35.7% / 27.4% |
| val | 128 / 45 | 0.352 | 0.02186 | 36.7% / 35.2% / 28.1% |
| test-dev | 128 / 27 | 0.383 | 0.04556 | 28.9% / 38.3% / 32.8% |

原路由在训练矩阵几乎总把图像级 top-1 判为 Window，而 oracle 分布明显多样，说明存在学习空间。

## 4. Utility Router 的迭代

训练使用缓存的目标层输入；检测器和专家冻结；相邻帧按视频序列分组，不能跨训练/验证边界。

| 版本 | 设计 | 内部验证 regret | 独立结果 | 新问题 |
|---|---|---:|---|---|
| A | 512 图，原 router，831 参数 | 0.02119 → 0.01225 | val 原始 0.02266，比基线 0.02186 差 | 内部提升不能外推 |
| B | A + 概率信任混合 `alpha=0.4` | 同上 | val 0.01966；test 0.05122 > 0.04556 | val 有效，test 失效 |
| C | 2,048 图 + 3 个场景统计残差，918 参数 | 0.03354 → 0.02345 | val 0.01737；test 0.05476 | 数据增加仍有域漂移 |
| D | C 改为 GAP+LayerNorm MLP，1,906 参数 | 0.03354 → 0.02288 | val 0.02700 | 容量增加反而过拟合 |

因此停止继续堆结构，改做安全门控。

### 4.1 KL 漂移保护

在 calibration val 上固定：

```text
alpha = 0.4
KL threshold = 1.5 * mean_KL_val = 0.00991753
```

- val KL=0.006612，不触发；regret `0.02186 → 0.01737`，下降 20.5%；
- test-dev KL=0.015411，触发；有效 `alpha=0`，regret 保持 `0.04556`；
- 若不保护，test-dev regret 会升到 0.05476。

这不是 test 提升，而是明确的“拒绝部署”机制。当前 utility router 仍未证明跨序列泛化。
以上数值来自 split 级离线门控；部署 context 另提供更保守的 batch 级 KL 门控，但尚未单独证明
其端到端 mAP。

## 5. Adaptive K

### 5.1 第一次实现的问题

第一版按图像平均概率选择全局专家池，即使 `K=2` 也会替换原来的逐 token Top-2。复审发现这让
“最大 K”不再等价于基线，会引入不必要的精度变化。

修正后：

- 仅当累计概率阈值允许 `K<2` 时收缩到图像级专家池；
- `K=2` 严格回退原逐 token Top-2；
- 训练模式始终固定 K；
- `-1` 表示 padding，不计入利用率；
- 直接记录实际 `expert_sample_calls`，不使用理论 K 冒充计算量。

### 5.2 128 图端到端复验

三轮测速每轮旋转顺序，至少预热 10 次且不少于 2 秒；汇总取三轮 percentile 的中位数。

| 变体 | mean K | 实际调用 | 调用下降 | mAP50-95 | P50 中位数 |
|---|---:|---:|---:|---:|---:|
| 原路由固定 K | 2.000 | 3.000 | 0% | **0.08743** | **26.877 ms** |
| utility 固定 K | 2.000 | 3.000 | 0% | 0.08700 | 30.519 ms |
| adaptive 0.35 | 1.242 | 1.484 | **50.52%** | 0.08695 | 28.244 ms |
| adaptive 0.36 | 1.594 | 2.188 | 27.08% | 0.08707 | 30.434 ms |
| adaptive 0.38 | 1.977 | 2.953 | 1.56% | 0.08697 | 28.135 ms |

固定 Top-2 的不同空间 token 合计会覆盖三个专家，所以基线实际调用为 3，而不是理论值 2。
首轮 P50 比后两轮高约 9-12 ms，原始三轮必须保留。调用量下降是确定性的；延迟没有随调用量
单调变化，adaptive 0.35 相对基线反而慢约 5.1%。原因是只改了六个 MoTBlock 中的一个，且
eager hook、router 重算和 Python 调度抵消了局部专家节省。

**最终判定**：

1. 检测效用 oracle 存在，支持继续研究 utility-aware routing；
2. 当前 utility router 在 calibration val 有效，但 test-dev 失败，只能带漂移保护实验使用；
3. adaptive K 可将目标层实际调用降低 50.52%，mAP50-95 绝对下降 0.00048；
4. 未证明端到端延迟显著下降，也未证明 mAP 提升，不能提交为稳定增益配置。

## 6. 下一步：何时引入 GRPO

现在直接做 GRPO 会放大不稳定 reward。更稳妥的顺序是：

1. 先训练“仅残差、冻结原 router”的低容量策略，并做多 seed、完整 val/test；
2. 将动作扩展为多层 `(expert_pool, K)`，奖励设为
   `-detection_loss - lambda*actual_calls - beta*KL_to_baseline`；
3. 用效用矩阵离线预热，再做带 KL/调用预算约束的 GRPO；
4. 预先固定 mAP 容忍区间和漂移阈值，test 只使用一次；
5. 只有多层真实调用下降转化为稳定 P50/P95 改善，才提交新 YAML 或默认策略。

当前阶段最有价值的结果不是“新路由更强”，而是建立了可审计的训练信号、失败检测和安全回退链路。
